**Phase:** 2 — System Integration

## Changed 2026-10-25

- **Acoustic data over LoRa decided** ([ADR-0010](../../decisions/0010-acoustic-summary-over-lora.md)).
  Each recording's 14-byte summary (three band levels, broadband level, approximate NDSI, snap
  and clip counts) goes in the packet, which grows from 30 to 44 B in schema v3. Not built yet:
  [SCO-233](https://linear.app/scout1/issue/SCO-233). Full ACI, ADI, the PCA score and compressed
  audio are ruled out. FFT bands and L90/L50/L10 levels wait on a bench test
  ([SCO-234](https://linear.app/scout1/issue/SCO-234)).
- **Found while researching:** the recording schedule disagrees across `config.h` (3 clips a day),
  the power budget (midnight and dusk windows plus a weekly diel day) and the EDD; the sample rate
  is 22.05 kHz in the build plan but 16 kHz in the EDD; the audio ADC is the Feather's 12-bit ADC
  in the build plan but the PCM1808 in the power budget. The `scout_packet.h` header comment still
  says 29 bytes. All are listed in SCO-233, not reconciled.

## Changed later on 2026-10-25 — acoustic summary built (SCO-233)

- **The ADR-0010 summary is implemented in software** ([SCO-233](https://linear.app/scout1/issue/SCO-233)):
  an integer-only Python reference (`analytics/utils/acoustic_summary.py`), a firmware port
  (`firmware/lib/scout_acoustic`) that matches it bit for bit on golden vectors, packet and CSV
  schema v3 (44 B; v1/v2 still decode), shore schema/store/import/simulator, and a Reef sound
  card and panel on the dashboard. Constants: snap at 8× the running mean, 3.0 ms refractory;
  clip within 16 counts of a rail; levels in centi-dB re full scale.
- **Not on hardware yet.** The capture path (SCO-231) is an interface that records nothing, so
  the buoy now reports `audio_present` = 0 instead of claiming scheduled clips. CPU headroom,
  dropped samples, recording current, anti-alias filter and amplifier gain are unverified; the
  filter chain is estimated at 48–57% of the M0 at 22,050 Hz.
- **Validated on Sesoko:** buoy NDSI vs shore NDSI Spearman ρ 0.91, `lvl_bio` vs shore BI ρ 0.46
  on 38 one-minute clips ([validation](../../analysis/acoustic-summary-validation.md)).
- **Found:** the shore pipeline's indices run at 44.1 kHz because `maad.sound.load` ignores the
  `sr` it is given ([SCO-235](https://linear.app/scout1/issue/SCO-235)). The schedule, sample-rate
  and ADC contradictions are now open facts in [`facts.md`](../facts.md); the stale
  `scout_packet.h` comment is fixed.

## Changed later on 2026-10-25 — audio capture written, contradictions settled (SCO-231, SCO-235)

- **Audio capture parameters decided** ([ADR-0011](../../decisions/0011-audio-capture-parameters.md)):
  3 × 60 s clips a day at 00/08/16 UTC, 22.05 kHz, the Feather's 12-bit ADC on A2. Settles the
  schedule, sample-rate and ADC disagreements between `config.h`, the power budget, the EDD and
  the build plan; every document now says the same. The power budget gained a dated update
  (≈ 2.8 mAh/day for audio, was 16.9; best-estimate life ≈ 24 months on one D cell).
- **Capture firmware written** ([SCO-231](https://linear.app/scout1/issue/SCO-231)): TC3 → event
  system → ADC → DMA ring → acoustic summary + WAV on SD. Compiles for the Feather; the WAV,
  conversion and dropped-sample logic is unit-tested natively; **never run**, because there is no
  hydrophone or preamp. RAM 23.2 of 32 KB.
- **Why capture lagged:** SCO-231 sat in Backlog behind the amplifier (SCO-216, Todo), the
  hydrophone order waits on funding (SCO-158), and `main.cpp` had labelled audio a "V1 stretch"
  while ADR-0005 put it in the V1 payload. The MVP overview's "stretch goal" label is now marked
  superseded.
- **SCO-235 fixed:** the shore indices really run at 22.05 kHz; results regenerated (BI ≈ ×4,
  verdict unchanged). The acoustic-summary validation was re-run against them (ρ 0.90 / 0.43).
- **Stale "hydrophone part open" references fixed:** SCO-8 has been Done since 2026-10-16 (H2dM).

## Changed later on 2026-10-25 — configurable transmit count and the team console (SCO-198)

- **Contradiction surfaced, not reconciled:** [SCO-197](https://linear.app/scout1/issue/SCO-197)
  is Done in Linear, but only the OTA *design* is; the buoy had no receive path. Recorded as an
  open fact in [`facts.md`](../facts.md) and on SCO-197.
- **Transmit count 1–3 a day built end to end in software** ([SCO-198](https://linear.app/scout1/issue/SCO-198)); the range is pending
  Isabella's power sign-off. Slots 1 → 00:10, 2 → 00:10 + 16:10, 3 → all; CONSERVE stays on slot 0.
  The buoy holds the count in retained RAM and reports it in packet **v4** (`flags` bits 8–9 +
  `CMD_REJECTED`; same 44 bytes; CSV gains `tx_count`). Shore and dashboard follow it; freshness
  no longer calls unscheduled slots missed.
- **Settings downlink built, off by default:** 1 s listen window + 28-byte HMAC-SHA256
  `SET_TX_COUNT` (`lib/scout_hmac`, `lib/scout_downlink`, Python mirror, golden vector in CI).
  Never run on hardware: listen-window current and timing, downlink range and the shore's FCC
  authorization to transmit are all unverified.
- **Battery-life model** (`analytics/telemetry/battery_life.py`): the count barely matters. 1 vs 3
  a day is 0.043 mAh/day, about 4 days over ~4 years on two cells. The count trades freshness,
  not lifetime.
- **Team console Phase A** ([ADR-0012](../../decisions/0012-authenticated-console.md)): Workers +
  D1, GitHub/Google/password sign-in, admin/member/guest, invites, audit log, fleet settings and
  the shore's device API. Built and tested, **not deployed**. A security review found no critical
  or high issues; its medium and low findings were fixed with tests. PBKDF2's 100,000 iterations
  turned out not to be a runtime cap, and take ≈ 10–11 ms locally, at the free-plan CPU limit.
- **Next:** adopt David's COR design system and Next.js app as the console front end, recoloured
  to Tideline, as a static export on the console API.
