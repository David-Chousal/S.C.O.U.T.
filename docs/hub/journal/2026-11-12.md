## Changed 2026-11-12 — shore station (David)

- **The shore station's WiFi is set up from a phone** ([SCO-310](https://linear.app/scout1/issue/SCO-310)).
  With nothing saved, or 10 s offline, it opens an open `SCOUT-Setup-XXXX` network whose page,
  styled like the console's sign-in, takes a network (any 2.4 GHz one, a phone hotspot included),
  its password and the device token, and saves them to flash. BOOT held 3 s or `W` over USB
  reopens it for 10 min. 29 new native tests (183 in all) and both shore builds pass; the page was
  checked against a fake station. ⚠️ Not yet run on the board.
- **Change WiFi on the console** reopens the setup network on a station that is still online: the
  settings reply carries the request for 15 min and the station now polls every minute (was 10).
  The setup page is light only. The open setup network is recorded as a security risk to fix
  before the product leaves the team ([SCO-311](https://linear.app/scout1/issue/SCO-311), Deferred).
## Changed 2026-11-12 — firmware (David)

- **Over-the-air firmware updates built** ([SCO-197](https://linear.app/scout1/issue/SCO-197),
  [OTA design §10](../../engineering/ota-firmware-update-design.md#10-as-built-2026-11-12)). The
  buoy side (signed offer, chunked transfer with resume from the SD card, SHA-256 and Ed25519
  checks, trial and `CONFIRM`), the `scout_boot` SD boot stub with A/B image slots and rollback,
  the S3 relay, the USB push script and the release signing tool. Behind `SCOUT_OTA`, **off in the
  shipped builds**. 23 new native tests, and the frames are held to the shore codec in CI.
  **Never run on hardware.** Packet `flags` gained `FW_TRIAL` (bit 11) and `FW_ROLLED_BACK` (bit 12).
- Found while building it: the stub is 21 KB with the Adafruit core, so it gets 24 KB and the app
  moves to `0x8000`. The signed image is 95.5 KB, not the 66.6 KB the design assumed, so an
  update is about 4–5 sessions and 12 mAh.
- Still open: the bench test, Isabella's listen-window sign-off, the FeatherWing FCC check, and the
  real signing key.
- **Settings path verified end to end in software, then OTA switched on.** A member's request in
  a local copy of the real console worker went through the S3's parser, the signed LoRa frame and the
  buoy's decoder; the buoy's next packet went back through the S3's row encoder and the console
  marked it **confirmed**. Only the radio and the WiFi transport were not exercised. On David's
  instruction `SCOUT_OTA` is now **on in the shipped `feather_m0` and shore builds**, which need
  `src/ota_pubkey.h` to compile. Found during the check and fixed: during a trial the shore now
  sends `CONFIRM` before pending settings.
- **Integration runbook and flashing guide brought up to date** for phone WiFi setup, Change
  WiFi, OTA (on in the shipped builds, never run on hardware, new gate G11), the open setup
  network (G12, [SCO-311](https://linear.app/scout1/issue/SCO-311)) and G10 (downlink and OTA on,
  FCC and listen-window sign-offs assumed, not recorded). Stage 0 re-verified today. Stage 4a is
  marked "reported working 2026-11-11, no record": it becomes ✅ only with a test record.

## Changed 2026-11-12 — console (David)

- **Firmware over WiFi decided and the console side built** ([ADR-0016](../../decisions/0016-firmware-delivery-over-wifi.md),
  [SCO-312](https://linear.app/scout1/issue/SCO-312)). An admin's API token with the new
  `write:firmware` scope uploads a signed `.scoutfw` bundle to `/api/v1/buoys/{id}/firmware`; the
  buoy's command station lists, downloads and reports on it under `/api/device/firmware`. The
  console checks the layout, size and image hash, never the signature. 17 new tests. Not
  deployed; D1 migration `0016-firmware-jobs.sql` not applied remotely. The S3 side, the release
  tool's `upload` command and the S3's own WiFi update are still to build.

## First-boot health check, round 2 (software)

- Second 12-vertical audit on top of [PR #321](https://github.com/David-Chousal/S.C.O.U.T./pull/321),
  tracked as [SCO-313](https://linear.app/scout1/issue/SCO-313) (round 1 had no Linear access, so
  the ticket was filed now). It reviewed round 1's changes and re-audited every vertical.
- Fixed: a buoy TX whose done-IRQ never fires left RadioHead stuck in TX, so the next send hung
  until the watchdog; the USB fallback sync pushed only the highest-numbered buoy's files;
  `push_firmware.py` could drop or truncate lines on a busy S3 and flushed the receiver's queued
  RX; the shore's `radio=FAIL` printed once and was invisible to the host receiver; a refused
  device token or a WiFi change while connected needed the BOOT button; the scout_boot stub
  header had no CI drift gate.
- New boot Serial: `power: battery_mv=… mode=…` (CRITICAL silences every TX, which looked like a
  dead radio on a bench supply) and `lora: TX skipped - radio init failed`.
- Checklist and Help corrected: SD in before the first flash, subshell `cd`, `rtc=ok` means the
  chip answered (clock set = no `RTC_LOST`), RESET after a shore radio fix, sync is one-shot,
  CRITICAL needs a charged pack, not a wait.
- **Surfaced, not reconciled:** [SCO-312](https://linear.app/scout1/issue/SCO-312) is Done in
  Linear but the S3 has no firmware-pull code (only the console half exists); the repo docs say
