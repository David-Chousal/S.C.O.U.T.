# Canonical Facts

> **Summary** — The single table of values every other document must agree with. When a doc
> contradicts this page, the doc is wrong — fix the doc, not this page (unless the fact itself
> changed, in which case change it here first and cite the decision that changed it).

> August 2026 audit found was a disagreement on one of these values.

## How to use this page

- **Reading a doc and something disagrees with this table?** This table wins. File it the way
  [CONVENTIONS.md → Decisions and disagreements](../CONVENTIONS.md#decisions-and-disagreements)
  says — surface it, don't silently reconcile.
- **A fact here actually changed?** Change it here **first**, in the same session, and put the
  source in the last column (an ADR, a measurement, a meeting). Then fix the docs that cite it.
- **Every value carries a source.** A number with no source is a number someone will build a
  power budget on. If it is an unverified estimate, say so in the value.

## Communications & data

| Fact | Canonical value | Source |
|---|---|---|
| LoRa modem config | **915.0 MHz · BW 500 kHz · SF12 · CR 4/8 · +11 dBm.** Bandwidth is set by compliance, not preference: 47 CFR §15.247 requires either ≥500 kHz 6 dB bandwidth or ≥50-channel hopping, and the previous BW125 single-channel config met neither. SF12 is then free to choose, and nets ~6.5 dB more link margin than the old BW125/SF7. ⚠️ **Register values and sensitivity are computed/modelled, not bench-verified** ([SCO-98](https://linear.app/scout1/issue/SCO-98)). Shore station must match exactly, plus the SX1276 500 kHz RX erratum | [FCC 915 MHz Compliance](../research/fcc-915-mhz-compliance.md), [SCO-19](https://linear.app/scout1/issue/SCO-19), `firmware/src/config.h` |
| RFM95 modular grant | **FCC ID `2ASEORFM95C`** (Shenzhen HOPE Microelectronics), Single Modular Approval, Part 15C, **equipment class DTS**. Binding conditions inherited by the end product: conducted power ≤ **0.0145 W (11.6 dBm)**, antenna gain ≤ **2.15 dBi**, no co-location with another transmitter, ≥20 cm separation from persons, and the enclosure must be labelled **"Contains FCC ID: 2ASEORFM95C"**. DTS is why BW500 is the certified mode and why frequency hopping would void the grant | [grant](https://fccid.io/2ASEORFM95C), [notes](research/notes/fcc-2aseorfm95c-modular-grant.md), [SCO-103](https://linear.app/scout1/issue/SCO-103) |
| LoRa range | **~2 km line of sight** (Adafruit RFM9x FAQ). Real over-saltwater range TBD in Phase 4 | [ADR-0001 reconciliation](../decisions/0001-mcu-and-radio-selection.md) |
| Daily packet | 1× per day — a summary, not a row dump. **Actual size is 30 bytes** (28-byte body + 2-byte CRC), encoded identically by firmware (`SCOUT_PACKET_SIZE`) and shore (`PACKET_SIZE`) and CI-enforced by `scripts/check_packet_contract.py`. The **82 bytes** in EDD §10/§14 is a different kind of number — the *payload budget ceiling* (`LORA_PAYLOAD_BUDGET_BYTES`), i.e. the most a daily packet may grow to, leaving ~52 bytes of headroom for future signals. Quote 30 B for what the buoy sends today and 82 B only when discussing the ceiling | [SCO-40](https://linear.app/scout1/issue/SCO-40), [Data Schema](../engineering/data-schema.md), EDD §10/§14 |
| Delivery scheme | **CR 4/8 + blind repetition** (3 copies NORMAL, 1 CONSERVE, widening gaps), never ACKed; shore deduplicates on `(buoy_id, record_seq)`. Spreading factor stays **SF7** — the stock CR 4/8 presets force SF12, which would overrun the TX budget and the FCC dwell limit | [SCO-21](https://linear.app/scout1/issue/SCO-21) |
| Raw audio over LoRa | **Never transmitted.** Stored onboard in `/AUDIO/`, retrieved physically | [EDD §10](../engineering/engineering-design-document.md) |
| Turbidity units | **The buoy ships raw ADC counts.** `turbidity_adc` (uint16) is the canonical on-board value and the packet field; `turbidity_v` is derived from it. `turbidity_ntu` is an **optional downstream column**, computed in the analytics pipeline only once a calibration curve exists ([SCO-12](https://linear.app/scout1/issue/SCO-12)) — it is left empty until then, and the buoy never computes it. Raw counts are lossless: a calibration applied downstream can be revised and re-run over historical data, while one baked in on-board cannot be undone | [SCO-13](https://linear.app/scout1/issue/SCO-13), [Data Schema](../engineering/data-schema.md), [decision log](decision-log.md) |
| Sample interval | ~30 min wake/sample cycle (turbidity + audio run less often) | [Data Schema](../engineering/data-schema.md) |

| Timestamps | **UTC**, ISO 8601 with trailing `Z` | [Data Schema](../engineering/data-schema.md) |

Sensor pod (2026-08-29): **AS568-137** face groove, 3-bolt Ø44.45 mm pattern. Both rely on the seal faces bottoming out land-to-land, so squeeze is set by geometry rather than bolt torque, with the flange stiffened against bolt-to-bolt bowing. **Seal elastomer: silicone** (chosen 2026-09-08, seawater + UV service, low compression set). ⚠️ **Provisional:** the clamp printed 2026-09-02 showed slight O-ring tolerance trouble ([SCO-105](https://linear.app/scout1/issue/SCO-105)), the AS568-043 ring's *free diameter* fit against the groove ID is still unverified ([SCO-106](https://linear.app/scout1/issue/SCO-106)), and **neither housing has been submersion-tested to this design** ([SCO-108](https://linear.app/scout1/issue/SCO-108)) | [SCO-68](https://linear.app/scout1/issue/SCO-68), [electronics-housing/README.md](../../mechanical/cad/electronics-housing/README.md#static-face-seal-clamp--2026-09-02), [sensor-housing/README.md](../../mechanical/cad/sensor-housing/README.md#face-seal-remodel--2026-08-29) |
